# Core-review
* [Review finding: "DV 5.1" is parsed as Dolby Vision profile 5, so the source is marked unplayable](bugs-library-dv-channel-layout.md) - The DV_PROFILE regex in parse/name.ts reads an audio channel layout after a DV tag (DV 5.1, DV 7.1) as the Dolby Vision profile, so a normal HDR release gets unplayableReason dv5 and auto-select never picks it.
* [Review finding: incremental source lists drop early partials and never signal completion with a synthetic part](bugs-library-incremental-partials.md) - In source-list.ts an addon that answers before the meta lookup finishes hits a temporal-dead-zone ReferenceError that aggregate swallows, so its streams.partial event is never sent; and when a meta-embedded or yt_id synthetic part exists, no partial ever carries remaining 0.
* [Review finding: marking the episode that is playing as watched is undone by the next progress report](bugs-library-mark-playing-watched-undone.md) - MarkVideoAsWatched advances the loaded item's video_id at once, unlike stremio-core's player which defers the advance to unload; the next progress report for the playing episode resets video_id and the watched flag, so continue watching returns to the episode and it can be counted watched twice.
* [Review finding: a migration cut short leaves the database half-migrated and core unable to start](bugs-library-migrations-not-atomic.md) - migrateToLatest runs Kysely's Migrator, which on SQLite runs each migration's statements without a transaction and records the migration only at the end; a full disk, crash or kill during a multi-statement migration leaves its first tables in place, unrecorded, and every later start fails with "table already exists" until someone repairs the database by hand.
* [Review finding: a playback never stopped is never unloaded, so continue watching sticks on a finished episode](bugs-library-no-idle-unload.md) - The library service applies stremio-core's unload rules (past 90 % clear the offset and move to the next episode) only on stop, ended, or a report for another video; a client that just goes away (tab closed, app killed, network lost, core restart) leaves the item on the finished episode at 95 %, and next returns that episode instead of the next one.
* [Review finding: one player model per profile corrupts watched state when two devices play](bugs-library-one-player-per-profile.md) - The library service keeps a single stremio-core player model per profile, so two devices of one profile playing different videos unload and reload each other on every report: the episode actually finished is never marked watched, another is marked by a spurious path, and timesWatched and overallTimeWatched inflate.
* [Core review: bugs-library progress](bugs-library-progress.md) - Progress, coverage, low findings and links to medium+ findings for the bugs-library area (addon collection and browse, selection and ranking, library, profiles, persistence and backups) of the core adversarial review.
* [Review finding: subtitle tags (ENG-SUB, VOSTFR, SUBFRENCH, Multi Subs) count as audio languages in ranking](bugs-library-subtitle-tags-as-audio.md) - parse/name.ts takes the release-name parser's languages as audio languages and ignores its subbed flag, so ENG-SUB gives a Korean-audio release the English bonus and VOSTFR gives an original-audio release the French mismatch penalty.
* [Review finding: torrent candidate keys ignore fileMustInclude and filename, so pack episodes share a key](bugs-library-torrent-key-file-choice.md) - A torrent candidate's key is built from infoHash and fileIdx only, but without fileIdx core chooses the file by fileMustInclude or behaviorHints.filename; two episodes of one pack get the same key, and listing one episode overwrites the stream store entry the other's key plays.
* [Every segment request runs an engine transcode to its end, HEAD and dropped requests included, with no bound](bugs-playback-detached-segment-amplification.md) - The gateway reads every segment's engine response to its end even for HEAD and for viewers already gone, and nothing caps these detached reads, so a media token holder can queue a full transcode of every segment of a title with a burst of cheap requests.
* [Session idempotency ignores the engine and highRes, so a different request gets the old session](bugs-playback-identity-ignores-engine-highres.md) - sessionIdentity hashes key, item, source, delivery and quality but not the requested engine or highRes, so a keyed create asking for another engine or high-res policy returns the existing session (200, created false) on the old engine with the old policy.
* [Engine sessions can outlive their playback session; nothing reconciles orphaned engine_sessions rows](bugs-playback-orphaned-engine-sessions.md) - An engine session whose playback session never recorded its sid (crash or DB error between the engine's master answer and commitReady, an aborted master whose cleanup DELETE fails) or that a concurrent master request recreates during release is never deleted, and on an engine with TTL 0 it stays forever.
* [Core review: bugs-playback progress](bugs-playback-progress.md) - Progress, coverage, low findings and links to medium+ findings for the bugs-playback area (sessions, engine module, gateway streaming lifecycle, events and SSE) of the core adversarial review.
* [Graceful shutdown never finishes while an SSE client is connected; held-back progress is lost](bugs-playback-shutdown-hangs-on-sse.md) - With any open GET /v1/events stream (the client always keeps one), RunningCore.close() never resolves, so the 10 s force-exit skips library.flush() and db.destroy() and exits 1, losing up to 90 s of held-back watch progress per playing profile on every restart.
* [Last-Event-ID from before a core restart can replay as "complete" and skip events](bugs-playback-sse-replay-after-restart.md) - Event ids are a counter that restarts at 1, so once the new run has issued as many events as the client's Last-Event-ID, a reconnect gets X-Events-Replay complete while missing every earlier event of the new run (session.failed interrupted, session.ready).
* [Core adversarial review (2026-10): charter, areas, finding format](charter.md) - Scope, threat model, review areas and workers, severity scale and the finding concept format for the pre-publication adversarial review of core (packages/core and packages/api).
* [Finding: problem bodies have no machine-readable kind, so clients must parse English detail text](design-api-error-model.md) - Every /v1 problem is `type: about:blank` with no error code; the same status means several different things (400, 409, 404 for a bad key), so an outside client can only branch on `detail` strings.
* [Finding: no pagination convention, an unbounded library response, and two list shapes](design-api-list-conventions.md) - The library route returns a profile's whole library (with every last source and player state joined in) on each call with no limit, sort or cursor; admin lists and /v1/catalogs are bare JSON arrays while client lists are envelopes, so the bare ones can't gain paging without a breaking change.
* [Finding: upgrades migrate in place with foreign keys on and no backup, so a routine table rebuild would erase libraries](design-api-migration-safety.md) - Migrations run on the live database with `foreign_keys = ON`; rebuilding a parent table the way migration 0005 did cascade-deletes every child row (PoC: a profiles rebuild empties library_items), and core takes no backup before applying migrations (scheduled backups are off by default).
* [Finding: core has no licence, so nobody may legally run, fork or build on it](design-api-no-licence.md) - There is no LICENSE file anywhere in the repository and no `license` field in any package.json; published as is, core would be all-rights-reserved. Runtime dependencies are all MIT or Apache-2.0, so any common licence is open.
* [A fresh install and its docs assume the maintainer's deployment](design-api-owner-specific-defaults.md) - Fixed 2026-10-20 to 2026-10-26: first start seeded an engine `home` with one mini-PC's capabilities and made it the default, the README described one deployment instead of a setup anyone can follow, and the API title, the addon User-Agent and the code comments carried the original project's name.
* [Core review: design-api progress](design-api-progress.md) - Progress, coverage, low findings and links to medium+ findings for the design-api area (/v1 API quality, architecture and boundary, configuration, persistence model, public readiness) of the core adversarial review.
* [Finding: the production wiring, upgrades with data and restore are untested, and CI is local only](design-api-test-gaps.md) - Vitest never plays through `startCore` (tests rebuild the composition root by hand, with auto-select's source list stubbed); the full root runs only in the Linux-only contract run and opt-in e2e; table-rebuild upgrades with data, down migrations and restore have no test; there is no coverage tool and no hosted CI.
* [Finding: the /v1 compatibility guard is not in CI, and the versioning promise contradicts itself](design-api-versioning-not-enforced.md) - The design says oasdiff runs in CI and additive-only changes stay in /v1, but `pnpm run ci` never runs api:diff, api:diff crashes on exit on Windows, and the changelog allows breaking /v1 changes with a minor bump.
* [externalUrl streams are listed but can never be opened](parity-external-url-hidden.md) - Streams whose only purpose is a link for the user to open (externalUrl and the platform variants) are listed as unplayable with the link withheld, so a client cannot do the one thing the addon protocol defines for them.
* [Live sources are ranked playable, but every live session fails](parity-live-sources.md) - Streams for tv and channel items are listed as kind live with playable true, while the engine module refuses any source whose probe has no duration, so live TV addons give a list that looks fine and a session that always fails.
* [Core review: parity matrix against stremio-core and the addon SDK](parity-matrix.md) - Capability by capability, whether core has, partly has, lacks or deliberately leaves out what stremio-core's models and types and the addon SDK protocol provide, as checked in the 2026-10 review.
* [Catalogs that answer metasDetailed always fail (Cinemeta last-videos, calendar-videos)](parity-metas-detailed-catalogs.md) - Core's catalog route only accepts a metas response, so Cinemeta's new-episode and calendar catalogs (which answer metasDetailed and take one comma-joined list of up to 100 ids) are listed by GET /v1/catalogs but every page fails.
* [No new-episode notifications or calendar, and no client-side way to build them](parity-notifications-calendar.md) - Core has no notifications or calendar for a profile's library series (stremio-core's update_notifications and calendar models), and because the addon catalogs that carry them fail through core, a client cannot build them on top either.
* [Which episodes are watched is only readable by decoding Stremio's bitfield](parity-per-video-watched.md) - There is no route that reads one library item or says which videos of a series are watched; a client must fetch the whole library and port stremio-core's zlib-compressed, anchor-aligned WatchedBitField to tick episodes in a list.
* [Core review: parity progress](parity-progress.md) - Progress, the parity matrix against stremio-core and the addon SDK, low findings and links to medium+ findings for the parity area of the core adversarial review.
* [A stream's own subtitles are parsed and then dropped](parity-stream-subtitles-dropped.md) - The addon protocol lets a stream carry its own subtitles (stream.subtitles), which Stremio's player adds as tracks; core parses them but neither the source list, the subtitle list nor a session's subtitles ever offer them.
* [Finding: the /v1 listener binds every interface over plain HTTP by default, with no warning](sec-access-api-listener-public-default.md) - Unset API_BIND means all interfaces and unset TLS means plain HTTP, so a bare `node dist/index.js` (or a `-p 8080:8080` publish as the Dockerfile's own header suggests) puts the admin-capable API on the network in cleartext; core logs no warning.
* [Core review: sec-access progress](sec-access-progress.md) - Progress, coverage, low findings and links to medium+ findings for the sec-access area (keys, scopes, media tokens, gateway, listeners, backups, CLI, logs, Docker) of the core adversarial review.
* [Finding: an open /v1/events stream keeps delivering after its API key is revoked](sec-access-sse-outlives-key-revocation.md) - The API key is checked only when GET /v1/events opens; revoking the key leaves an already open SSE stream (heartbeats keep it alive) delivering every event, admin-only ones included, until the client disconnects or core restarts.
* [Addon resource requests follow redirects to private and loopback hosts](sec-input-addon-redirect-ssrf.md) - The addon HTTP client follows up to 20 redirects to any host with no address check, so a public addon can make core send GETs to the engine or other LAN hosts on every catalog, meta, stream or subtitle request.
* [Core adds the engine proxy password to addon-supplied engine /proxy URLs](sec-input-engine-proxy-password.md) - A plain url stream pointing at the engine's own loopback /proxy/stream gets core's stored api_password appended, so a hostile addon passes the proxy password gate and reaches proxy-only allowlisted hosts through the media routes.
* [Core's own outbound fetches have no private-host guard (subtitle URLs, addon redirects)](sec-input-outbound-ssrf.md) - Subtitle file URLs and addon response redirects let a hostile addon make core GET loopback and LAN hosts, including the engine's unauthenticated control routes, which only core is supposed to reach.
* [Core review: sec-input progress](sec-input-progress.md) - Progress, coverage, low findings and links to medium+ findings for the sec-input area (hostile addon input, SSRF, fetch limits, validation, parsing, SSE and metrics abuse) of the core adversarial review.
* [Quadratic regexes on addon text freeze core (ReDoS)](sec-input-redos.md) - Several regexes in subtitle conversion and stream-name parsing run in quadratic time on addon-controlled text, so one hostile stream or subtitle file blocks core's event loop for minutes to hours.
* [Subtitle file fetch reaches private and loopback hosts (SSRF)](sec-input-subtitle-ssrf.md) - Core fetches addon-supplied subtitle URLs and follows redirects with no private-host guard, so a hostile addon can make core read LAN hosts or the engine and hand converted bytes to media-token holders.
* [Addon-sized data is cached by count, not bytes](sec-input-unbounded-memory.md) - The addon response cache (1000 entries) and the events replay buffer (1000 events) are bounded by count only, while each addon response may be 8 MiB, so a hostile addon can grow core's heap to gigabytes.
