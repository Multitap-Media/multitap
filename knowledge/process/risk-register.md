R-numbers are stable identifiers: never renumber them. Numbers missing from the list belonged to risks of the apps built on Multitap.

| # | Risk | Mitigation |
|---|---|---|
| R1 | **Software decode on the reference engine host** with 3.5× pre-roll: measured in phase 0, 4K takes 6–11 s per 4 s segment and 1080p HEVC 10-bit tops out at 2 live sessions | ≤1080p live, 4K only prepared ([[concept/source-ranking]]). GPU decoding comes to the engine, upstream or on the fork ([[process/engine-upstream-prs]]): 4K SDR in ~1.6 s, three at once. No pre-roll (#30) saves 38–62% at 4K on its own. Single-viewer clients can avoid the transcode with direct play ([[concept/delivery-modes]]). |
| R2 | HDR tone mapping is CPU-bound, and DV P5 renders with a green/purple cast (#27 skips it, logging only at debug) | #27's mobius tone map is correct for HDR10 and DV 8.1. Rank SDR first and exclude DV P5 until the GPU pipeline's libplacebo path (Reference engine hardware and measured performance), the only one that renders DV P5 correctly. |
| R3 | Single rendition: the slowest viewer's downlink limits the room | Bitrate sized for the weakest viewer ([[architecture/rendition-and-bandwidth]]), per session through `quality` (#25). The planned ABR ladder ([[architecture/rendition-and-bandwidth]], R30) removes the limit. |
| R5 | ~~Global TTL and no delete: idle sessions stay 48 h~~ **Retired.** | Fixed by #24 and #25: core deletes sessions and the TTL is a safety net ([[architecture/engine-retention]]). Only an engine older than v0.18.0 needs the 48 h TTL and the disk for it (Reference engine configuration). |
| R6 | Engine restart loses all sessions, including preparations | Mostly resolved: #26 makes sessions survive (`STREMIO_HLS_PERSIST=1`), and #34 (v0.18.1) fixes the v0.18.0 bug that discarded them with TTL `0` or a per-session `ttl` (seen on the reference engine host). The reference engine runs a build with the fix ([[process/engine-upstream-prs]]), verified by a restart test. Verification + re-queue ([[architecture/engine-prepare-ahead]]) stays as the fallback; plan restarts before preparation windows. |
| R7 | Core is in the media path: a core restart or redeploy interrupts playback | hls.js retries plus master self-heal. Deploy Multitap when nobody is watching. A client restart doesn't interrupt playback. |
| R8 | A viewer disconnect can kill an in-flight segment transcode | The gateway doesn't abort upstream `.ts` requests ([[architecture/media-gateway-proxy]]). Verified in phase 0; phase 2's gateway tests keep it covered. |
| R9 | YouTube: `/yt` needs a progressive format, which YouTube withholds on and off (phase 0: mostly `404`), and yt-dlp needs a JavaScript runtime | deno machine-wide on the engine box; the engine moves to DASH video + audio ([[process/engine-upstream-prs]]), which also fixes the 360p quality. Later: YouTube IFrame player synced via its API. |
| R10 | Debrid: each segment is ~6 range requests, each paying the host's first-byte latency (~420 ms for Real-Debrid), so a segment takes 3.5–12 s on the shipped pipeline | Phase 0 saw no 429/503, even with parallel ranges. Prepare debrid sources, or play them live only with a fast engine; the engine's header/index cache ([[process/engine-upstream-prs]]) cuts a segment to one request. |
| R12 | Legal/ToS exposure of torrenting from the engine's IP | Operator's decision. VPN recommended. Explicit consent for remote engines ([[architecture/future-remote-engines]]). |
| R18 | **Broken segments cached** (TS seeks landing late, truncated input; ffmpeg exits 0) | #29 serves them without caching and retries TS once with a 30 s pre-roll. Left: a segment cut short, which #29 doesn't detect (the short-segment check, [[process/engine-upstream-prs]]); until then, reload a visibly broken source in a fresh session. |
| R19 | **ffmpeg 8.0.1 hangs on some MKV seeks** until the segment timeout (180 s). Watch item: not reproduced on the engine's 9.0.2 build. | ffmpeg audio-filter issue, not server-go (ffmpeg 8.0.1 can hang on some MKV seeks via aresample,apad). Only matters on an engine running 8.x; the buffering give-up keeps one stuck segment from pausing the room. |
| R20 | ~~**Windows read flakiness**: ffmpeg reading loopback URLs on Windows intermittently failed on the dev machine~~ **Closed.** | Not seen on the reference engine host (200 clean segments in phase 0), so the engine stays on Windows. #29 prevents caching the damage if it appears. |
| R21 | Future engine changes (the unfiled items in [[process/engine-upstream-prs]]) don't merge, or merge in a different shape | Everything filed so far (#24–#29, #33–#36) merged. Every design point has a fallback on an engine without the change ([[process/engine-upstream-prs]], [[architecture/engine-retention]]); if upstream declines one, carry it on a fork. |
| R23 | **Media tokens leak** from URLs (logs, shared links, referrers) | Scoped to one session, expiring, revocable per subject; redacted in core's logs at `info` and above (proxy logs are the operator's policy); `Referrer-Policy: no-referrer` ([[architecture/media-gateway-proxy]], [[architecture/secrets-policy]]). |
| R24 | ~~**`proxyHeaders` sources fail on the reference engine**: it sets `STREMIO_PROXY_PASSWORD`, and core never sends `api_password`~~ **Fixed 2026-10-01** (found in phase 2) | A secret, write-only `proxyPassword` on the engine descriptor (API or CLI), sent as `api_password` by the engine module; the first use of the outbound-credential rule ([[architecture/secrets-policy]]). Left: the operator sets it on `home`, and keeps it in step with the engine's value. |
| R25 | **`prom-client` is deprecated**: npm marks it as replaced by `@prometheus-io/client` | Fixed 2026-10-01: core moved to `@prometheus-io/client` 0.16.1. Metrics sit behind `metrics/`, so the swap touches one module. |
| R26 | **Two enum additions in responses are flagged by `api:diff`** against `main`: the `metrics` value of `ApiKey.scope` (admin key routes) and the addon `status` value `needs-configuration` (catalog, meta, streams and subtitles responses) | The first was accepted by the maintainer on 2026-10-01 (admin clients only); the second on 2026-10-04. Both are in the `core-v0.1.0` baseline, so later `api:diff` runs against the tag don't show them. `api:diff` exists to show such changes, which is why tagging `core-v0.1.0` waited until the end of phase 2 ([[process/build-plan]]). |
| R27 | ~~**A failed engine `DELETE` leaks the engine session** on an engine with TTL `0`: core marks the playback session released and doesn't retry, and sends no per-session `ttl`~~ **Fixed 2026-10-01** (found in phase 2) | The release stays pending and the retention sweep retries it with backoff until the engine confirms (`204`/`404`); `ENGINE_SESSION_TTL_MS` optionally sends a long per-session `ttl` as the safety net ([[architecture/engine-retention]]). |
| R28 | **A weak viewer stalls a full-quality session** (observed 2026-10-01: a phone on a weak cell signal, engine 10M, ~9 Mbps segments taking 5–7 s per 4 s) | One rendition per session ([[architecture/rendition-and-bandwidth]]): size `quality` for the slowest viewer; `maxHeight: 480` (derived 1.5 Mbps) played smoothly. |
| R30 | **Building core against an assumed engine feature** (the ladder, [[process/engine-upstream-prs]]): upstream may decline or change the shape, and QSV behaviour is untested: several QSV encoders in one process on Windows oneVPL, QSV HEVC encode on the reference engine host, and per-segment times for 2–3 rungs (AV1 encode is probably unavailable on that iGPU). Also a first request of a lazy rung may bias a player's bandwidth estimate (untested with hls.js), a silent libx264 fallback multiplies by the rung count, and a mixed-codec ladder strands a viewer who can't decode one codec | The `ladder` capability gates everything (an engine without it keeps one rendition), so core's ladder code is exercised against the fake engine only until a real one has it; if upstream declines, carry it on the fork (R21). Measure on the reference engine host before enabling in a room; keep a ladder's codec set decodable by every viewer; default to H.264. |
| R31 | **The third-party segment service disappears or changes its terms** (IntroDB or any later provider, [[architecture/segments-module]]): hosted, community-run, with terms and licence not yet checked | The module is optional (`MULTITAP_SEGMENTS_PROVIDERS` empty by default), isolated (timeouts, circuit breaker, metrics; off the playback path, so a failure never affects sessions or sources), and swappable behind the provider interface without touching core. Check terms and episode addressing before relying on a provider; cache long, one User-Agent and rate limit; skip buttons simply don't appear when there is no data. |
| R33 | **The engine's probe cache can return a bad result** (found 2026-10-06 with a MediaFusion source: 1280x720, 120 s and one AAC track recorded; the real file is 1920x1080, 634.6 s, MP3 and AC3). The playlist ended at 2:00, the `maxHeight` cap wasn't applied and a track was missing. A retry of the same source reuses the cached probe. Cause unconfirmed (hypothesis: a placeholder on the first request) | Open, documented only. Candidates: core re-probes or rejects when the duration disagrees badly with the meta's runtime; an upstream ask for a probe-cache bypass or TTL ([[process/upstream-engine-asks]]). Gather evidence first: probe twice, compare, check the cached entry ([[architecture/engine-prepare-stream]]) |
| R34 | **Anime id coverage differs across addons**: AIOMetadata's anime episodes use `kitsu:` ids, and MediaFusion's stream resource accepts only `tt`, `tmdb:`, `tvdb:`, `mal:`, `mf` and `dl` prefixes (`mal:` and `tvdb:` ids also found nothing in the test), so core asks no addon and returns an empty source list with no hint why. `mal:` and `kitsu:` ids for one show also become two library items | Open, documented only. Options: fall back to the IMDb id from the meta's links with season and episode, or an id-mapping step (a design change); configure AIOMetadata to output IMDb ids; an additive hint in the empty source list naming the unmatched prefix |
