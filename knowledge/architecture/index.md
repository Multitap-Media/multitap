# Architecture
* [Planned ABR ladder: core side (request, identity, capability, players)](abr-ladder-core-api.md) - How core would expose the planned ABR ladder: the ladder form of quality, identity and caps, capability fallback, production policies, cost, codecs, gateway and load, and the open watch-party and devices questions. Nothing here is built.
* [Addon private-host guard (MULTITAP_ADDON_PRIVATE_ALLOW)](addon-private-host-guard.md) - How core keeps addon-chosen URLs off the engine and the LAN: every hop an addon controls (addon redirects, subtitle files) must reach a public address, checked on the literal and at connect time, unless the operator's MULTITAP_ADDON_PRIVATE_ALLOW lists it.
* [Boundary rule: Multitap knows nothing about the apps built on it](boundary-rule.md) - Features that only make sense with several viewers, several devices or people belong in clients, never in Multitap; inside the repository, dependency-cruiser enforces which package may import which.
* [Configuration: what a setting is, and core's environment variables](configuration.md) - What counts as a setting (env for startup limits, database for runtime preferences, code for protocol facts) and the full table of core's configuration (read by docs:check against EnvSchema).
* [Core: API keys and media tokens (security view)](core-api-keys-security.md) - API keys are 32 random bytes stored hashed, with client, admin and metrics scopes; the client holds a client key and an admin key used only behind a step-up; core's API listener is docker-internal and answers 404 without a key; media tokens are scoped, expiring and revocable.
* [Building and testing the core API: zod-openapi, Schemathesis, oasdiff, fakes](core-api-testing.md) - How core's API is built and tested: routes declared once with zod and @hono/zod-openapi, generated client, Schemathesis contract tests with stateful links, oasdiff against the last release, the client's equivalent, Prism, what the contract cannot cover, fakes, and why not tRPC.
* [Multitap deployment: two listeners, CORS and TLS, no proxy required](core-deployment.md) - Multitap listens on 8080 for /v1 and 8081 for /media, each private or public; a CORS allowlist, optional built-in TLS and absolute media URLs, so a reverse proxy is one option, never a requirement.
* [Core events: SSE stream, replay and incremental source lists](core-events-sse.md) - GET /v1/events server-sent events: event types, filters, heartbeat, the bounded replay buffer with Last-Event-ID and the X-Events-Replay header, and incremental source lists answered with 202 and streams.partial events.
* [Core modules: the planned module tree and how phase 2 named it](core-modules.md) - The module tree of core (addons, selection, engine, sessions, library, gateway, segments, api, cli) with the section each module is specified in, and how packages/core/src names them as built in phase 2.
* [Core persistence: tables, migrations 0001 to 0011, backups and restart](core-persistence.md) - Core's SQLite tables (addons, engines, api_keys, profiles, last_sources, item_player_states, library_items, playback_sessions, engine_sessions, session_subtitle_offsets, prepare_jobs, token_revocations, settings), the full migrations list, online backups and restore, and restart behaviour.
* [Core scope: what core owns and what it never knows](core-scope.md) - Core is a standalone headless Stremio client with a remote engine; it owns addons, source lists, engines, playback sessions, media delivery and profiles, and knows nothing of rooms, members, roles or sync.
* [Core subtitles, timing offset, per-item player state and search extras](core-subtitles-and-player-state.md) - Session subtitle tracks under the media token, the server-side subtitle timing offset (limits, semantics, storage), per-item player state (P1, core 0.1.3), and how search and subtitle extras (videoHash, videoSize, filename) are fanned out.
* [Core /v1 API: routes, scopes, delivery, error behaviour and versioning](core-v1-api.md) - Core's /v1 API listener: the complete route table (docs:check reads it), bearer API-key scopes, the admin routes built so far, delivery and mediaPath, error behaviour as built, versioning, and using Multitap from your own app.
* [Engine ABR ladder: one decode, many encodes (scoping, design)](engine-abr-ladder-design.md) - Scoping of an upstream ABR ladder for stremio-server-go: why one per-segment ffmpeg run can decode once and emit every rung, why long-running ffmpeg is rejected for live, where chunked runs belong (preparation), the maintainer's 2026-10-01 direction, per-request rungs and the three production policies.
* [Engine ABR ladder: filter graph, hardware, session, master and persistence changes](engine-abr-ladder-engine-changes.md) - What the ladder changes inside stremio-server-go: the multi-output filter graph, the GPU pipeline shape (D3D11VA to QSV split and vpp_qsv per rung), the silent libx264 fallback hazard, per-request rung overrides and validation, naming, locking, master playlist branch, persistence without bumping the format version.
* [Engine endpoints core uses, and engine facts core relies on](engine-endpoints-core-uses.md) - The stremio-server-go endpoints core calls, how core detects DELETE support, builds engine-local mediaURLs, picks the torrent file and keeps trackers; plus the torrent idle-timeout lifecycle.
* [stremio-server-go HLS transcode model](engine-hls-model.md) - How the engine transcodes: caller-keyed sessions, independent on-demand 4-second segments with 10 s pre-roll, software decode, one H.264 rendition, cache, eviction, probe cache, SSRF guard and tuning.
* [Core engine module: interface and responsibilities](engine-module.md) - The only core code that knows stream internals and engine APIs: the EngineModule interface (prepare, status, release, fetchMedia), the EngineHandle, and how phase 2 built it. Transport, preparation, lifecycle, ahead-preparation and retention are in their own concepts.
* [Preparing ahead: lead times, who does what, verification (phase 4, not built)](engine-prepare-ahead.md) - Planned preparation of a full-mode session by its readyBy: lead times by source height, the engine-side versus core-driven paths, verification at readyBy minus 10 minutes, uncached segments, and progress reporting.
* [Preparing a stream for playback: steps, unplayable reasons and the resolution matrix](engine-prepare-stream.md) - The five prepare steps (engine session id, resolve mediaURL, probe, create the session, warm the start), the probe-caching hazard, the table of unplayable reasons with retryability, and the matrix mapping a raw Stream to a mediaURL.
* [Engine private-host allowlist (STREMIO_PROXY_PRIVATE_ALLOW, STREMIO_HLS_PRIVATE_ALLOW)](engine-private-host-allowlist.md) - How the engine lets named LAN hosts through its SSRF guard: two separate allowlist settings for /proxy and for mediaURL, listed addresses only, resolved at connect time.
* [Engine session retention: policy, release and pending-release retries](engine-retention.md) - Retention policy in core (max of retainUntil and lastAccess plus idle), how upstream #24 and #25 change enforcement, the sweep as built, release racing a resolution, retried pending releases (R27), and the optional per-session ttl.
* [Engine has no auth and must be reachable only by core](engine-security-posture.md) - stremio-server-go has no authentication; it is reachable only by core on the LAN. The SSRF guard protects the LAN from addon-supplied URLs, not the engine's own endpoints.
* [Engine session lifecycle during playback: self-heal and admission](engine-session-lifecycle.md) - How an engine session behaves while a viewer plays: self-healing master requests, no keepalive, no seek prewarm from core, and admission against the engine's liveConcurrency (warn, reject or off) measured as load.
* [Engine transport, health checks and re-check on an answer](engine-transport-and-health.md) - How core talks to an engine: the lan transport (timeouts, connect timeout, no Origin, no redirects), the future tunnel, health checks with exponential backoff, the immediate re-check when an offline engine answers (2026-10-05), and why core polls.
* [Future work: remote engines and local content](future-remote-engines.md) - Not planned for v1: a friend's engine (helper app with an outbound tunnel, pairing code, allowed-paths-only agent, consent for torrenting, capability reporting) and the maintainer's local library on the reference engine through upstream PRs #31 and #32; the seams already in place.
* [Goals and non-goals](goals-and-non-goals.md) - What Multitap is for (a headless Stremio client with a remote engine that any client can use, deployable on its own) and what it deliberately leaves out (people, UI, Stremio accounts, a diverging engine fork).
* [Notes from IDEAS.md: the few ideas that touch core](ideas-that-touch-core.md) - How core's design leaves room for the undecided ideas that touch it: pre-roll, lobby and intermissions as separate playback sessions, Plex account linking and Plex LAN URLs behind the engine's SSRF guard, voice chat outside the gateway, and everything else belonging in clients.
* [Last source per (profile, item)](last-source-per-item.md) - When a session created with profileId becomes ready, core records the source in last_sources, one row per (profile, item); source lists flag it lastUsed and auto-select ranks it up.
* [Core profiles, Stremio-format library and last source](library-and-profiles.md) - Profiles own settings and library items in Stremio's library format; core applies stremio-core's progress and watched rules; last source per (profile, item) lives in its own concept; the client maps every account but admins to a profile.
* [Media gateway proxy behaviour: authorization, streaming, CORS, disconnects, telemetry](media-gateway-proxy.md) - How the gateway proxies: in-process token authorization, unbuffered streaming and response headers, CORS, not aborting segment requests on viewer disconnect, several viewers on one transcode, timeouts, per-viewer telemetry, the browser CSP finding of 2026-10-01, and token hygiene in logs.
* [Media gateway: URL scheme, status codes, retry, cost and live](media-gateway.md) - Core's media listener on its own port: the /media URL scheme with its filename allowlist, relative playlists, check order and status codes, the one-time segment retry (2026-10-14), Range handling, cost, and live (phase 4). Proxy behaviour is a separate concept.
* [Network exposure: listeners, binds, proxies and the engine](network-and-deployment-exposure.md) - What may face which network in a Multitap deployment: the media listener may face the internet, the /v1 API stays private or uses TLS (with a startup warning otherwise), and the engine is reachable from Multitap only.
* [Normalized addon types (packages/api): SourceCandidate and friends](normalized-addon-types.md) - The normalized types clients see instead of raw addon data: CatalogRef, MetaPreview, MetaDetail and SourceCandidate with its parsed fields, playable flags and unplayable reasons; raw Stream objects stay in core.
* [Multitap system overview](overview.md) - The three pieces around Multitap: the streaming engine it drives (stremio-server-go is the one tested), Multitap itself (addons, sources, sessions, media gateway, library) and the clients built on its /v1 API, and how a playback flows between them.
* [Core playback session: one source per session, keyed idempotency](playback-session.md) - A playback session binds one chosen source to one engine session; its status lifecycle, idempotent creation by key, fixed delivery and source, and how media is reached.
* [One rendition per session; per-session quality and bitrate by height](rendition-and-bandwidth.md) - Today a session has one H.264 rendition; core lets a create set maxHeight and bitrate (capped by core), with a height-to-bitrate table; the room's quality must suit its slowest viewer.
* [Secrets: no central holder, the classes, the Secret wrapper and the engine password](secrets-classes-and-engine-password.md) - Decided 2026-10-01: no central secrets holder. The five secret classes with direction, storage and lifecycle; the Secret wrapper, one rule for outbound credentials, consistent rotation; and the first use, the write-only engine proxy password (built 2026-10-01, R24).
* [Secrets: transit, redaction and logging policy](secrets-policy.md) - What core fetches from addon-supplied URLs, how manifest URLs and raw streams stay in core (and transit through the client as Secrets), backup downloads as the admin exception, no referrer on media tokens, the info-versus-debug logging rule, proxies outside core, and the client's secrets and log redaction including redactEmail.
* [Security principles and trust domains](security-trust-domains.md) - Multitap's trust domains (hostile addons, a public media listener, API key holders trusted within their scope, an unauthenticated engine, non-expert operators) and the rule that the API reveals nothing to a caller without a key.
* [Segments: optional skip intro/outro module (planned)](segments-module.md) - Planned optional core module for skip-segment data (intro, outro, recap, credits, preview): not an addon, provider interface in packages/segments, GET /v1/segments/{type}/{id}, caching and isolation, the IntroDB and AniSkip providers, timing and the client's part. Decision 2026-10-04.
* [Runtime and tooling choices](toolchain.md) - Node 26 and pnpm 12, the tool chosen for each area and why (Hono + zod-openapi, Vitest, Playwright, pino, Prometheus client, jose, better-sqlite3, Kysely, Renovate…), what is wrapped or written in-house, and what is deliberately not used.
