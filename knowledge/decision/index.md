# Decision
* [ABR ladder design (planned, maintainer decisions 2026-10-01)](abr-ladder.md) - Planned engine feature: one decode with many encodes, per-request rungs, hybrid production policy by default, capability-gated as `ladder`, and a codec caveat for mixed viewers. Not built; core is built against a fake engine first.
* [Captured addon responses are redacted before commit; never add an unredacted fixture](fixtures-redaction-rule.md) - Rule for packages/addon-protocol test fixtures: real addon responses are captured and redacted (stream URLs replaced, proxy header values replaced, credentials replaced, internal blobs removed, Torrentio trimmed). Never add a fixture containing a real stream URL, a manifest URL with configuration, a key, a username or a password.
* [Client picks by default; auto-select falls back through candidates](auto-select-and-fallback.md) - Starting playback: a picked source has no fallback and fails visibly; auto-select ranks, prepares the first candidate and tries the next on failure, with attempt and time limits, one torrent retry, failure reasons, and binge and last-source bonuses.
* [Core licence: AGPL-3.0-only for core, MIT for the client packages, DCO without a CLA](core-licence.md) - Decision (2026-10-20): core (packages/core and its image) is AGPL-3.0-only so hosted forks stay open; @multitap/api and @multitap/addon-protocol are MIT so clients can use any licence; contributions are signed off under the DCO, with no CLA. Everything else in the repository (scripts, docs, the knowledge bundle) is AGPL-3.0-only under the root LICENSE (2026-10-29).
* [Destructive catalog items are flagged, never hidden or auto-picked](destructive-items-flagged.md) - Items and sources whose names match destructive phrases (delete all, wipe, format…) carry a `destructive` flag; they stay listed, never change a score, and auto-select never picks them. Found when a MediaFusion watchlist entry looked like it would empty a debrid account.
* [Multitap's repository starts with fresh history](core-public-repo-fresh-history.md) - Decision 2026-10-25: Multitap is published from its own repository whose git history starts fresh (first commit tagged v0.2.0, 2026-10-29, the private work before it squashed in), with nothing carried over from the project it was built in; the release record before that lives in the CHANGELOG.
* [Nothing assumes a reverse proxy](no-reverse-proxy-dependency.md) - Multitap must work with no reverse proxy in front: built-in TLS, a CORS allowlist and public media URLs from configuration; a proxy (Traefik, Caddy, nginx or any other) is an optional variant, never a dependency.
* [Releases need no per-release approval](release-without-approval.md) - Maintainer decision 2026-10-29: when finished work warrants a release, bump, tag vX.Y.Z and push it without asking first, although the tag publishes the GHCR image and a GitHub release; never force-push.
* [Schema-first API: zod-openapi, generated client, contract tests](contract-first-api.md) - Core's /v1 routes are declared once with zod schemas; the OpenAPI document and client are generated, never hand-written. Schemathesis, oasdiff and Prism check and use it. tRPC and oRPC were rejected.
* [The public name is Multitap](core-public-name-multitap.md) - Decision 2026-10-25: the project is published as Multitap. Why the name, the namespaces registered for it (GitHub org Multitap-Media, npm @multitap, multitap.dev, ghcr.io/multitap-media) and the names it sets for packages, image, CLI, variables, metrics and files.
* [stremio-core is a reference for types and rules, not a dependency](stremio-core-reference-not-base.md) - Core is written in TypeScript; stremio-core (Rust) supplies protocol types and library-item rules only, because shimming its WASM build costs more than the code it would save.
